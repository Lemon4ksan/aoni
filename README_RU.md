## Почему Aoni?

Разработка современных Go-приложений часто требует объединения множества независимых сетевых библиотек - отдельного управления HTTP/3, uTLS, DoH/DoQ резолверами, WebSockets, gRPC-Web и ретраями. Использование разрозненных пулов памяти и моделей контекста приводит к повышенной нагрузке на сборщик мусора (GC), всплескам задержек и дублированию кода.

`aoni` объединяет современные стандарты RFC IETF, спецификации W3C и механизмы сетевой надежности уровня Chromium в единую архитектуру.

Независимо от того, выполняются ли стандартные запросы к REST API микросервисов, высоконагруженная маршрутизация на API-шлюзе, реалтайм-потоки WebSockets или задачи сетевого анализа, `aoni` обеспечивает пути выполнения с нулевыми аллокациями и предсказуемым бюджетом памяти.

### 💡 Зачем aoni быть таким быстрым, если CRUD измеряется в миллисекундах?

Сетевой транспорт в `aoni` спроектирован так, чтобы стать абсолютно невидимым для системы и не отбирать ресурсы CPU у бизнес-логики. Даже если ваш CRUD-сервис отвечает за 10–20 миллисекунд из-за запросов к базе данных, 0 B/op и 500 нс задержки транспорта кардинально меняют характеристики системы:

1. **Микросервисный Fan-Out (Каскадное умножение)**: 1 входной запрос на API Gateway порождает 5+ исходящих вызовов (Auth, Search, Payments, WAF, Cache). На `aoni` служебный транспорт «растворяется» в ~2.5 мкс и 0 B/op вместо 90 000+ аллокаций в секунду на 1000 пользователей.
2. **0% GC Mark-Assist на транспорт**: Транспорт не мусорит в куче (`mheap`). Процессор тратит 100% мощности на полезную работу (БД, JSON, бизнес-правила), а не на служебную гигиену сборщика мусора.
3. **Запас прочности под пиковой нагрузкой (SLA P99.9)**: В Чёрную Пятницу или при DDoS тяжёлые клиенты задыхаются от аллокаций, вызывая спайки задержек P99.9. `aoni` сохраняет предсказуемый плоский график задержки.
4. **Сокращение Cloud TCO**: Снижение потребления памяти в 2–19 раз позволяет обслуживать в 3–5 раз больше одновременных WebSocket/HTTP соединений на том же инстансе K8s/AWS.

## Быстрый старт

### 1. Универсальный Generic-интерфейс (`FetchTo`)

```go
package main

import (
	"context"
	"fmt"
	"time"

	"github.com/lemon4ksan/aoni"
	"github.com/lemon4ksan/aoni/fluent"
	"github.com/lemon4ksan/aoni/mod"
	"github.com/lemon4ksan/aoni/option"
)

type User struct {
	ID   int    `json:"id"`
	Name string `json:"name"`
}

func main() {
	ctx := context.Background()

	client := aoni.NewClient(nil,
		option.WithBaseURL("https://api.example.com"),
		option.WithTimeout(15*time.Second),
		option.WithChrome(), // Готовый профиль Chrome, ECH, 0-RTT и устойчивость к сбоям
	)

	// Выполнение запроса, валидация и декодирование в 1 вызов
	user, resp, err := fluent.FetchTo[User](ctx, client, "GET", "/users/{id}",
		mod.WithVar("id", 123),
		mod.WithHeader("X-Custom-Header", "value"),
	)
	if err != nil {
		panic(err)
	}

	fmt.Printf("User: %s (Status: %d)\n", user.Name, resp.StatusCode)
}
```

## Архитектура и Двойной Движок

`aoni` предоставляет два исполнительных движка под единой моделью API:

```
               ┌──► aoni.Client (100% совместимость с net/http и цепями middleware)
option / mod ──┼
               └──► fast.Client (2.14M+ RPS multi-core, zero-alloc fasthttp + H2/H3)
```

* **Стандартный `aoni.Client`**: Используется, когда требуется 100% совместимость со стандартной библиотекой Go и инфраструктурой `net/http`.
* **Нативный `fast.Client`**: Используется, когда необходимы максимальная пропускная способность и геометрия памяти с 0 B/op аллокаций.

## Профиль производительности и бенчмарки

Чтобы объективно оценить конвейер выполнения, бенчмарки разделены на две категории: **Параллельная многопоточная пропускная способность** (измеряет конкуренцию за блокировки аллокатора памяти при высокой нагрузке) и **Последовательная однопоточная задержка** (измеряет чистое время выполнения одного запроса в памяти).

### 1. Параллельная многопоточная пропускная способность (12 ядер CPU, `b.RunParallel`, PGO-Оптимизировано)

При высокой параллельной нагрузке на всех ядрах процессора аллокатор памяти Go (`mcache`/`mcentral`) начинает испытывать конкуренцию за блокировки. Поскольку `aoni` выполняет **на 12 аллокаций меньше** за запрос, чем стандартный `net/http` (66 против 78 аллокаций), он намного лучше масштабируется, обеспечивая **задержку на 10% ниже** в стандартном режиме и **в 3.4–18 раз более высокую производительность** в режимах Bridge и Native.

| Метрика | Стандартный `net/http` | `aoni` (Стандартный) | `aoni` + `fast.Bridge` | `aoni/fast` (Нативный) | Разница производительности |
| :--- | :---: | :---: | :---: | :---: | :---: |
| **Анмаршалинг GET JSON (`GetTo[T]`)** | 55 532 ns | 55 710 ns | **11 862 ns** | **5 572 ns** | **В ~4.7 раза быстрее (Bridge) / в 10 раз (Native)** |
| **Чистое исполнение (`c.Request`)** | 6 899 ns | **6 236 ns** | **3 834 ns** | **3 809 ns** | **Быстрее Stdlib и сырого fasthttp (3 858 ns)** |
| **Память в куче (`B/op`)** | 6 898 B | **5 853 B** | **4 458 B** | **362 B** | **В ~1.18 раза легче (Standard) / в 19 раз (Native)** |
| **Аллокации (`allocs/op`)** | 78 allocs | **66 allocs** | **49 allocs** | **8 allocs** | **-29 аллокаций (Bridge) / 8 аллокаций (Native)** |
| **Задержка HTTP/2 (`ns/op`)** | 79 253 ns | 79 253 ns | **68 026 ns** | **68 026 ns** | **В 2.08 раза меньше памяти в H2 (4.5KB против 9.3KB)** |
| **Задержка HTTP/3 (`ns/op`)** | 127 431 ns | 127 431 ns | **121 975 ns** | **121 975 ns** | **На 50% меньше памяти в QUIC (11.5KB против 23.3KB)** |
| **Параллельная задержка (`ns/op`)** | 11 307 ns | 9 534 ns | **1 940 ns** | **566.4 ns** | **В ~4.9 раза быстрее (Bridge) / в 20.0 раза (Native)** |
| **Параллельная память и GC (`B / alloc`)** | 6 898 B / 78 | 5 853 B / 66 | 2 218 B / 19 | **0 B / 0 allocs** | **Ноль аллокаций в куче** |
| **Пиковая пропускная способность** | ~35k RPS | ~30k RPS | >80 000 RPS | **2 080 000+ RPS** | **Экстремальный I/O** |

### 2. Последовательная однопоточная задержка (1 ядро, `b.N`)

При конфигурации `aoni.Client` с помощью `option.WithBaremetal()` отключаются защитные механизмы Chromium-уровня (определение WAF-челленджей, декомпрессия, валидация ответов) и включается выделенный быстрый путь. Оба клиента выполняются последовательно в один поток на одном и том же транспорте `fasthttputil.InmemoryListener`.

| Бенчмарк | `net/http` | `aoni` (Baremetal) | Оверхед |
| :--- | :---: | :---: | :---: |
| **Чистый GET (`c.Request` + дренаж тела)** | 17 205 ns / 5 870 B / **67 allocs** | **16 697 ns** / 6 046 B / **67 allocs** | **Raw Aoni БЫСТРЕЕ (-508 нс, 0 лишних аллокаций)** |
| **Обобщённый GET + JSON decode (`request.GetTo[T]`)** | 19 342 ns / 6 813 B / **74 allocs** | **20 186 ns** / 8 973 B / **75 allocs** | +1 аллокация (+4.3% времени) |

> [!TIP]
> **Почему `aoni` обгоняет `net/http` при параллельной нагрузке?**
> Высокая пропускная способность в стандартных HTTP-клиентах Go вызывает частые паузы сборщика мусора (GC) и заторы в аллокаторе памяти `mcentral`.
> Стандартный движок `aoni.Client` делает **на 12 аллокаций меньше** за запрос, чем `net/http` (66 против 78 аллокаций, 5.8KB vs 6.8KB), снижая нагрузку на аллокатор рантайма при многопоточном исполнении. В это же время `aoni/fast` (Native) повторно использует буферы через `PerPStorage` (нуль межядерных блокировок), задействует интернирование заголовков `.rodata`, SIMD AVX2/BMI2 интринсики (`simd_amd64.s`), нетемпоральную потоковую запись и профильную оптимизацию PGO (`default.pgo`), работая с **0 B/op и 0 allocs/op** в параллельном I/O при плоской задержке **566.4 нс ± 1%** и пропускной способности **2.08M+ RPS** на одном сервере. Профилирование процессора (`pprof`) подтверждает, что собственный код обертки `aoni` потребляет **ВСЕГО 0.34% времени CPU**, оставляя 99.66% ресурсов процессора исключительно под сетевой сокетный I/O.

> [!NOTE]
> **Объяснение производительности в однопоточном режиме**
> При однопоточном исполнении (1 ядро, 0% параллелизма) сырой путь `aoni` выполняется за **16.69 мкс** с **ровно 67 аллокациями/запрос**, опережая чистый `net/http` (17.20 мкс). За счет устранения промежуточного клонирования контекста `http.Request` и повторного использования ссылок `BaseURL`, `aoni` полностью сровнялся по количеству аллокаций с `net/http`, обеспечивая при этом превосходящее масштабирование на многоядерных серверах.

## Структура Репозитория

```
aoni/
├── option/       // Опции инициализации клиента (option.With...)
├── mod/          // Модификаторы запросов (mod.With...)
├── request/      // Generic-хелперы (request.GetTo[T], PostTo, PostProtoTo)
├── fast/         // Движок высокой производительности на базе fasthttp
├── fluent/       // Цепочный Builder API (fluent.R, FetchTo[T], Codec)
├── cookie/       // Прокси-изолированные куки, формат Netscape, сортировка по RFC 6265
├── fingerprint/  // Обход TLS/JA4/p0f отпечатков, кадры HTTP/2, CDN-паддинг
├── netutil/      // Ротатор прокси, DoH/DoT DNS резолверы, ротатор IPv6 подсетей
├── codec/        // Декодеры ответов (JSON, Proto, gRPC-Web, XML) и кодирование параметров
├── realtime/     // WebSocket поверх H2 CONNECT, Socket.IO v5, SSE и NDJSON потоки
├── resiliency/   // Кэширование ответов, детекторы/солверы WAF, балансировщик нагрузки
└── telemetry/    // Генератор HAR, отслеживание задержек EWMA, веб-дашборд инспектора
```
